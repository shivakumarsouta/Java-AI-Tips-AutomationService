Pass‑by‑Value Semantics in Java: Object References vs Primitive Types

Published on 2026-09-18 10:17:32 • Topic: Pass-by-Value Semantics in Java (Object reference pass-by-value vs pass-by-reference)
▼

1. Core Mechanics & Internal Architecture

In Java every argument is passed by value. For primitive types the value is the raw data (e.g., int, double). For objects the value is the reference (a memory address) that points to the actual heap object. The method receives a copy of that reference; both the caller and callee refer to the same object, but reassigning the parameter only changes the copy, not the caller's variable. This is why mutating the object's fields is visible after the call, while assigning a new object to the parameter is not.

2. Production‑Grade Java Implementation

Example showing a mutable object, an attempted swap, and a legitimate state change.

class Point {
    int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
    @Override public String toString() { return "(" + x + "," + y + ")"; }
}

public class PassByValueDemo {
    static void trySwap(Point a, Point b) {
        Point temp = a;
        a = b;          // only the local copy of the reference changes
        b = temp;
    }

    static void move(Point p, int dx, int dy) {
        p.x += dx;      // mutating the object through the shared reference
        p.y += dy;
    }

    public static void main(String[] args) {
        Point p1 = new Point(1, 1);
        Point p2 = new Point(5, 5);
        trySwap(p1, p2);
        System.out.println(p1); // prints (1,1) – not swapped
        move(p1, 3, 4);
        System.out.println(p1); // prints (4,5) – state changed
    }
}

3. Performance, Memory & JVM Tuning Gotchas

Because only the reference value is copied, the overhead is constant regardless of object size, but careless aliasing can lead to unintended shared‑state bugs, especially with mutable collections. Avoid exposing internal mutable objects; prefer immutable data or defensive copies. When profiling, watch for excessive object churn caused by creating temporary wrapper objects solely for method calls.

4. Top Interviewer Trap Questions & Deep Answers

Q1: If a method reassigns its object parameter to a new instance, does the caller see the new instance?
A1: No. The method works with a copy of the original reference; reassigning that copy does not affect the caller’s variable. Only mutations on the object that both references point to are reflected back.

Q2: Why can a method modify the fields of an object passed as a parameter, even though Java is pass‑by‑value?
A2: The value passed is the reference to the object. Both caller and callee hold references that point to the same heap instance, so changing the instance’s fields modifies the shared object. The “pass‑by‑value” rule still holds because the reference itself is copied, not the object.

Virtual Threads (Project Loom) in Java 21

▼

Key Gotchas: Avoid pinning virtual threads to platform carrier threads by replacing synchronized blocks with ReentrantLock during blocking I/O calls.

try (var executor = java.util.concurrent.Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 100_000; i++) {
        final int taskId = i;
        executor.submit(() -> {
            // High throughput blocking network call
            java.util.concurrent.TimeUnit.MILLISECONDS.sleep(100);
            return taskId;
        });
    }
} // AutoCloseable executor awaits completion

Java Garbage Collectors: G1 vs ZGC Differences and Use Cases

Published on 2026-09-09 09:05:20 • Topic: Java Garbage Collectors (G1 vs ZGC differences and use cases)
▼

Overview: The JVM provides specialized garbage collectors tailored to different latency and throughput requirements. G1 (Garbage-First) is the default collector since Java 9, while ZGC (Z Garbage Collector) is a low-latency collector introduced in Java 15+.

Core Mechanics:

  • G1 GC: Divides the heap into equal-sized regions (1MB to 32MB). It uses concurrent marking and incremental compaction targeting a configurable pause goal (-XX:MaxGCPauseMillis).
  • ZGC: Employs colored pointers and load barriers to perform nearly all GC phases concurrently with application threads, achieving sub-millisecond pause times regardless of heap size.
// Example JVM flags for selecting Garbage Collectors
// Enable G1 GC (Default in JDK 9+):
// java -XX:+UseG1GC -XX:MaxGCPauseMillis=200 -jar app.jar

// Enable ZGC (JDK 15+):
// java -XX:+UseZGC -XX:+ZGenerational -jar app.jar

Interviewer Gotchas: ZGC trades slightly lower single-thread throughput for ultra-low pause latency. If throughput is the primary metric over pause latency, G1 or Parallel GC may be preferable.
